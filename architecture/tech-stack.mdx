The Scanmex Logistics Tracker is built across two distinct application layers that serve different users with different hardware, yet both depend on the same underlying data. The **web dashboard** is used by logistics staff on desktop browsers to plan routes and monitor drivers in real time. The **Android app** runs on Zebra rugged terminals carried by drivers in the field. Both layers connect through a shared data layer — SQL Server as the primary database and SAP Business One as the company ERP — ensuring that an action taken on one application is immediately visible in the other.

## Web Dashboard

The dashboard was built with technologies suited for a server-rendered, data-intensive logistics interface. Razor pages generated by ASP.NET Core deliver fast initial loads, while JavaScript handles the interactive map layer after the page is in the browser.

| Technology | Role |
|---|---|
| C# | Server-side logic |
| HTML5 | Screen structure |
| CSS3 | Visual design |
| JavaScript | Map and interactivity |
| SQL | Database queries |

## Android App

The mobile application targets Zebra rugged Android terminals — devices built for warehouse and delivery environments that include physical barcode scanners. The stack reflects the standard Android development toolchain plus the Zebra-specific SDK needed to drive the hardware scanner.

| Technology | Role |
|---|---|
| Java / Kotlin | Android Studio logic |
| XML | Screen layouts |
| Geolocation API | GPS position reporting |
| Zebra SDK | Barcode/laser scanner integration |

## Shared Data Layer

Both the web dashboard and the Android app read and write through a single **SQL Server** instance, which acts as the source of truth for routes, driver locations, delivery confirmations, and application credentials. On top of the relational database, the system integrates with **SAP Business One via its Service Layer** — an OData v4 REST API that bridges the logistics workflow with the company's ERP. When a driver confirms a delivery on the Zebra terminal, the confirmation travels to SQL Server, and the server then calls the SAP Service Layer to update the corresponding sales order, eliminating any need for manual re-entry in SAP.

## Design Tooling

Before writing a single line of Razor markup or Android XML, the screens for both applications were wireframed in **Stitch** — Google's AI-assisted UI design tool that generates interface layouts from a written description. The dashboard views (route map, delivery table, driver assignment panel) and the driver-facing screens (stop list, barcode scan confirmation) were prototyped in Stitch first, giving the team a visual reference to implement accurately in Razor templates and Android XML layouts.

<Tip>
  Both the web dashboard and the Android app connect to the **same SQL Server instance**. This means a route assigned in the dashboard appears on the driver's terminal immediately, and a delivery confirmed on the terminal is reflected in the dashboard in real time — there is no separate sync job or data duplication between the two applications.
</Tip>
